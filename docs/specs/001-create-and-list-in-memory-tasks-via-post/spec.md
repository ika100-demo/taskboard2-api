# 001 — Create and list in-memory tasks via POST /tasks and GET /tasks

## Problem

The taskboard2 system has no way to record work yet: a caller of the taskboard2 API cannot add a task or see the tasks it already added. This is the first feature of the system, and every later one (completing, editing or filtering tasks) needs tasks to exist. For now the tasks only have to live as long as the service runs, so callers can try the system before any storage is set up.

## System context

Slice of the system plan `001-create-and-list-tasks` in `ika100-demo/taskboard2-gitops` for `taskboard2-api` (service-python). The system criteria and the contract below are binding: every criterion of this spec implements one of them and names it: `(system AC-<NNN>.<n>)`.

### System criteria

- **AC-001.1** Given the API is running, when a caller sends `POST /tasks` with the JSON body `{"title": "Buy milk"}`, then the response is `201` with a JSON object holding a non-empty `id`, `title` equal to `"Buy milk"` and `due_date` equal to `null`.
- **AC-001.2** Given the API is running, when a caller sends `POST /tasks` with `{"title": "File taxes", "due_date": "2026-12-01"}`, then the response is `201` and the returned task has `due_date` equal to `"2026-12-01"`.
- **AC-001.3** Given a task was created, when a caller sends `GET /tasks`, then the response is `200` with a JSON array that contains an object with that task's `id`, `title` and `due_date`, exactly as returned at creation.
- **AC-001.4** Given no task has been created since the service started, when a caller sends `GET /tasks`, then the response is `200` with an empty JSON array `[]`.
- **AC-001.5** Given tasks A, B and C were created in that order, when a caller sends `GET /tasks`, then they appear in the order A, B, C (oldest first).
- **AC-001.6** Given two tasks were created with the same title, when a caller lists the tasks, then both appear and their `id` values differ.
- **AC-001.7** Given the API is running, when a caller sends `POST /tasks` with no `title`, with `title` not a string, or with a `title` that is empty or only whitespace, then the response is `422` with a JSON error body that names the field `title`, and no task is added to the list.
- **AC-001.8** Given the API is running, when a caller sends `POST /tasks` with a `title` longer than 200 characters, then the response is `422` with a JSON error body that names the field `title`, and no task is added; a title of exactly 200 characters is accepted.
- **AC-001.9** Given a title with leading or trailing whitespace, such as `"  Buy milk  "`, when the task is created, then the stored and returned `title` is `"Buy milk"`.
- **AC-001.10** Given the API is running, when a caller sends `POST /tasks` with a `due_date` that is not a calendar date in the form `YYYY-MM-DD` (for example `"tomorrow"`, `"2026-02-30"` or `"2026-12-01T10:00:00Z"`), then the response is `422` with a JSON error body that names the field `due_date`, and no task is added.
- **AC-001.11** Given today is 2026-11-05, when a caller creates a task with `due_date` `"2026-01-01"` (in the past), then the task is created with that due date.
- **AC-001.12** Given tasks were created, when the service restarts, then `GET /tasks` returns an empty array `[]`.

### Contract

Base URL: the service root (dev: `http://taskboard2-api.taskboard2-dev.localhost:8088`). JSON in and out,
`Content-Type: application/json`. No authentication.

### Task object

| Field | Type | Notes |
|---|---|---|
| `id` | string | Non-empty, generated by the service (UUID4 in canonical text form); unique within the process. Never supplied by the caller. |
| `title` | string | 1 to 200 characters after trimming leading and trailing whitespace; stored and returned trimmed. |
| `due_date` | string or `null` | Calendar date `YYYY-MM-DD` (ISO 8601 date only, valid day of month), or `null` when not given. Past dates allowed. |

The response object has exactly these three fields. The service returns `due_date` exactly as the normalized date
(`"2026-12-01"`), always present, `null` when absent.

### `POST /tasks`

Request body: a JSON object.

| Field | Required | Rules |
|---|---|---|
| `title` | yes | Must be a JSON string (no coercion of numbers, booleans, etc.); after trimming, length 1 to 200. |
| `due_date` | no | Absent or `null` means no due date. Otherwise a JSON string matching exactly `YYYY-MM-DD` that is a real calendar date; date-times, other formats and non-strings are rejected. |

Unknown fields are ignored. Validation of both fields happens before anything is stored; on any `422` no task is added.

Responses:
- `201 Created` with the created task object as body.
- `422 Unprocessable Content` when the body is not valid JSON, is not a JSON object, or a field breaks the rules above
  (format under Errors).

### `GET /tasks`

No parameters (filtering, sorting and pagination are non-goals; unknown query parameters are ignored).

Responses:
- `200 OK` with a JSON array of task objects, oldest first (creation order), every task created since the process
  started. `[]` when there is none. Each object is identical to the one returned by its `POST /tasks`.

### Errors

Every `422` uses the FastAPI/pydantic validation format:

```json
{"detail": [{"loc": ["body", "title"], "msg": "<human-readable message>", "type": "<error type>"}]}
```

- `detail` is a non-empty array; each entry names the offending field as the last element of `loc`
  (`"title"` or `"due_date"`). When both fields are invalid, both appear. A body that is not JSON or not an object
  has `loc` `["body"]` (or `["body", <position>]`).
- `msg` and `type` are informative only; callers and tests must not depend on their exact text, only on the
  status code and the field name in `loc`.
- Other statuses come from the framework and are not part of this feature: `405` for another method on `/tasks`,
  `404` for an unknown path, `500` on an unexpected failure (JSON `{"detail": "..."}` or empty body).
- A caller treats any status not listed for an endpoint as a failure of that call and must not assume the task was
  created; it may list the tasks to find out.

### Timeouts

- The service makes no outgoing calls for this feature; both endpoints answer from memory and should respond well
  under 100 ms.
- Callers (including the smoke tests) use a 10 s timeout per request, matching `tests/test_smoke_health.py`.
  On timeout or connection error, the caller reports the call as failed; a `POST` that timed out may or may not
  have created the task (there is no idempotency key), so a caller that retries can create a duplicate, which
  AC-001.6 allows.
- When the service is down or restarting, requests fail at the Gateway (`502`/`503`) and, after the restart, the
  list is empty (AC-001.12); this is expected behaviour, not an error to handle.

### Notes for this repo

Smoke checks: mark AC-001.1, AC-001.2, AC-001.3, AC-001.7 and AC-001.10 as smoke criteria; they can be
checked through the public URL (`@pytest.mark.smoke`, `SMOKE_BASE_URL`, like tests/test_smoke_health.py).
The dev deployment is shared and keeps its tasks between smoke runs, so a smoke test never assumes an
empty list: it finds the task it created by `id`, and for a 422 it checks that the list length did not
grow from its own request. AC-001.4, AC-001.5, AC-001.6, AC-001.8, AC-001.9, AC-001.11 and AC-001.12 are
in-process tests only (they need a fresh store, a restart or exact ordering on an empty list).
Storage: a process-local, in-memory store (list in insertion order) behind a small interface, created
in the app factory so each test app and each restart starts empty. No database, no new env vars.

## Stories

As a caller of the taskboard2 API, I want to create a task with a title and an optional due date, so that I can record a piece of work.

As a caller of the taskboard2 API, I want to list every task created so far, oldest first, so that I can see what work is recorded.

As a caller of the taskboard2 API, I want invalid input rejected with an error that names the offending field, so that I can correct my request and never end up with a half-valid task.

## Acceptance criteria

- **AC-001.1** Given the service is running, when a caller sends `POST /tasks` with the JSON body `{"title": "Buy milk"}`, then the response is `201` with a JSON object that has exactly the fields `id`, `title` and `due_date`, where `id` is a non-empty string, `title` is `"Buy milk"` and `due_date` is `null`. (system AC-001.1) (smoke)
- **AC-001.2** Given the service is running, when a caller sends `POST /tasks` with `{"title": "File taxes", "due_date": "2026-12-01"}`, then the response is `201` and the returned task has `title` `"File taxes"` and `due_date` `"2026-12-01"`. (system AC-001.2) (smoke)
- **AC-001.3** Given a caller created a task with `POST /tasks` and kept the returned object, when it sends `GET /tasks`, then the response is `200` with a JSON array in which exactly one element has that `id`, and that element is equal to the object returned at creation (same `id`, `title` and `due_date`); other tasks in the array are ignored. (system AC-001.3) (smoke)
- **AC-001.4** Given a freshly started service in which no task has been created, when a caller sends `GET /tasks`, then the response is `200` with the body `[]`. (system AC-001.4)
- **AC-001.5** Given a freshly started service, when tasks A, B and C are created in that order and a caller sends `GET /tasks`, then the array has three elements whose `id` values are those of A, B and C in that order. (system AC-001.5)
- **AC-001.6** Given a freshly started service, when two tasks are created with the same title `"Buy milk"`, then `GET /tasks` returns two elements, both with title `"Buy milk"`, and their `id` values differ. (system AC-001.6)
- **AC-001.7** Given the service is running and a caller has read the length of `GET /tasks`, when it sends `POST /tasks` with a body that has no `title`, with `title` set to a non-string (for example `123`, `true` or `null`), with `title` `""` or with `title` `"   "`, then each response is `422` with a JSON body whose `detail` array contains an entry whose `loc` ends with `"title"`, and a following `GET /tasks` returns an array no longer than the one read before the request. (system AC-001.7) (smoke)
- **AC-001.8** Given a freshly started service, when a caller sends `POST /tasks` with a `title` of 201 characters (after trimming), then the response is `422` with a `detail` entry whose `loc` ends with `"title"` and `GET /tasks` returns `[]`; and when it sends a `title` of exactly 200 characters, or 200 characters surrounded by spaces, then the response is `201` with that 200-character title. (system AC-001.8)
- **AC-001.9** Given a freshly started service, when a caller sends `POST /tasks` with `{"title": "  Buy milk  "}`, then the returned task has `title` `"Buy milk"`, and the element for it in `GET /tasks` also has `title` `"Buy milk"`. (system AC-001.9)
- **AC-001.10** Given the service is running and a caller has read the length of `GET /tasks`, when it sends `POST /tasks` with `title` `"Buy milk"` and a `due_date` of `"tomorrow"`, `"2026-02-30"`, `"2026-12-01T10:00:00Z"` or the number `20261201`, then each response is `422` with a JSON body whose `detail` array contains an entry whose `loc` ends with `"due_date"`, and a following `GET /tasks` returns an array no longer than the one read before the request. (system AC-001.10) (smoke)
- **AC-001.11** Given today is 2026-11-05, when a caller sends `POST /tasks` with `{"title": "Old task", "due_date": "2026-01-01"}`, then the response is `201` and the returned task has `due_date` `"2026-01-01"`. (system AC-001.11)
- **AC-001.12** Given tasks were created in a running service, when the service is restarted (a new service instance is started) and a caller sends `GET /tasks`, then the response is `200` with the body `[]`. (system AC-001.12)

## Non-goals

- Persistence: no database or any storage that survives a restart; tasks live in the memory of the running process only.
- A front end or any user interface.
- More than one replica: the list is only consistent while exactly one instance serves requests.
- Filtering, sorting and pagination of `GET /tasks` (unknown query parameters are ignored).
- Updating, completing or deleting tasks.
- Authentication and authorization.
- Idempotency of `POST /tasks` (a retried request may create a duplicate).
