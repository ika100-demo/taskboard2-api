# Design — 002 Persist tasks in Postgres behind the existing TaskStore, answering 503 when the database is down

The HTTP contract is the one of spec 001 (see `docs/specs/001-create-and-list-in-memory-tasks-via-post/design.md`,
`## Contract`), plus the new `503`. The system contract restated in the spec (`### Contract`) is binding; this
document only adds what this repo's coders and testers need.

## Decisions

- **Swap the store, keep router and schemas.** As spec 001's design planned, `create_app()` picks the store:
  `PostgresTaskStore(DATABASE_URL)` when `DATABASE_URL` is set and non-empty, else `InMemoryTaskStore()` (in-process
  tests, local runs; spec non-goal: deployed without a database). `tasks_api.py` and `task_schemas.py` do not change.
  `DATABASE_URL` is read when `create_app()` runs, not at import, so tests set it with `monkeypatch.setenv` before
  calling `create_app()`; the module-level `app = create_app()` (Dockerfile, `conftest.py`) reads the process env.
- **Store failures are one domain exception, mapped to `503` in one place.** `task_store.py` gets
  `class TaskStoreUnavailable(Exception)`. `PostgresTaskStore` wraps every `psycopg.Error` (connection errors,
  `psycopg_pool.PoolTimeout`, query errors, statement timeouts: all subclasses) in `raise TaskStoreUnavailable() from exc`.
  `create_app()` registers an exception handler for it that returns
  `JSONResponse(status_code=503, content={"detail": "Task store unavailable"})` and logs one structured warning
  (`event="task_store_unavailable"`, `error=<exception class name>`; never the URL or the driver message, which may
  contain the host or user). The router never sees psycopg (AC-002.6, AC-002.9).
- **Validation stays in front of the store.** FastAPI validates the body before the handler runs, so an invalid
  body answers `422` without touching the database, even when it is down (AC-002.8). No change needed; it must not
  regress (no store access in a dependency that runs before validation).
- **Driver: psycopg 3 with `psycopg_pool.NullConnectionPool`.** The null pool opens a connection in the requesting
  thread on checkout and closes it on return: a request during an outage fails fast with the driver's error, and the
  very next request after the database is back simply connects (AC-002.7, AC-002.9). A regular `ConnectionPool`
  reconnects in background workers with exponential backoff (up to `reconnect_timeout`), which is exactly the
  background retry loop the spec excludes and would delay recovery by an unbounded backoff step. The cost, one
  connection setup per request, is a few milliseconds in-cluster and irrelevant at this service's load.
  Parameters: `NullConnectionPool(conninfo=DATABASE_URL, max_size=10, timeout=2.0, open=True,
  name="taskboard2-api-tasks", kwargs={"connect_timeout": 2, "options": "-c statement_timeout=3000",
  "application_name": "taskboard2-api"})`. `max_size=10` caps concurrent connections per replica (2 replicas stay far
  below Postgres' default 100); `timeout=2.0` is the checkout wait when all 10 are busy. Opening the null pool does
  not connect, so the service starts and `/health`, `/ready` answer `200` with the database down (AC-002.9).
  Dependency `psycopg[binary]` bundles libpq, so the slim runtime image needs no system package.
- **Schema created by the service, lazily, under an advisory lock.** `PostgresTaskStore` holds
  `_schema_ready: bool` guarded by a `threading.Lock`. Every operation checks out a connection and, while
  `_schema_ready` is false, first runs in its own transaction `SELECT pg_advisory_xact_lock(<SCHEMA_LOCK_KEY>)` then
  the spec's `CREATE TABLE IF NOT EXISTS tasks (...)` verbatim, commits (releasing the lock), and sets the flag. The
  transaction-scoped variant of `pg_advisory_lock` is used so the lock can never outlive a failed attempt. A failure
  leaves the flag false, so the next request tries again; startup never touches the database (AC-002.4, AC-002.9).
  `SCHEMA_LOCK_KEY` is a module constant `7_202_002_001` (any fixed bigint; only this service uses the database).
- **Ids generated by the service, ordering by `seq`.** `add` generates `uuid.uuid4()` in Python (as the in-memory
  store does), inserts `(id, title, due_date)` and returns `Task(id=str(id), ...)`; `seq` is filled by the identity
  column. `list_all` runs `SELECT id, title, due_date FROM tasks ORDER BY seq` and maps rows to `Task(str(id), title,
  due_date)` (psycopg returns `uuid.UUID` and `datetime.date`). Each operation is one transaction
  (`with pool.connection() as conn:` commits on success, rolls back on error), so a failed `POST` stores nothing
  (AC-002.1, .2, .3, .6). UUID4 collisions across restarts and replicas are not a practical concern; the primary key
  turns one into a `503`, never a duplicate.
- **Pool closed on shutdown.** `PostgresTaskStore.close()` closes the pool; `create_app()` installs a FastAPI
  `lifespan` whose shutdown part calls `close()` when the store has it. Startup does nothing, so a `TestClient` used
  without `with` (as the spec 001 tests do) still works.
- ADR: [docs/adr/001-postgres-task-persistence.md](../../adr/001-postgres-task-persistence.md) (driver, null pool,
  service-managed schema without a migration tool: these outlive this feature).

### Public interfaces (signatures only)

```python
# task_store.py
class TaskStoreUnavailable(Exception):
    """The backing store could not be reached or failed; maps to HTTP 503."""

# postgres_task_store.py
SCHEMA_LOCK_KEY: Final = 7_202_002_001

class PostgresTaskStore:                        # implements TaskStore
    def __init__(self, conninfo: str) -> None: ...   # opens the NullConnectionPool; never connects
    def add(self, title: str, due_date: datetime.date | None) -> Task: ...   # raises TaskStoreUnavailable
    def list_all(self) -> list[Task]: ...       # oldest first (ORDER BY seq); raises TaskStoreUnavailable
    def close(self) -> None: ...                # closes the pool; idempotent

# main.py
def create_app() -> FastAPI: ...                # reads DATABASE_URL at call time
app: FastAPI                                    # = create_app()
```

## Contract

Unchanged from spec 001 for `201`, `200` and `422` (fields, validation, error format). New:

- `GET /tasks`, `POST /tasks` with a valid body: `503 Service Unavailable`, `Content-Type: application/json`, body
  exactly `{"detail": "Task store unavailable"}`, for any connection, pool-timeout or query error of the database.
  Nothing is stored. Worst-case latency about 2 s (connect timeout) or 3 s (statement timeout), inside the 5 s of
  AC-002.6.
- `POST /tasks` with an invalid body: `422` as in spec 001, whatever the database state (AC-002.8).
- `GET /health`, `GET /ready`: `200` regardless of the database (AC-002.9; spec non-goal: database health in `/ready`).
- Configuration: `DATABASE_URL` (libpq URI or key/value conninfo). Unset or empty: in-memory store.

### For the acceptance tests

- In-process, against a real Postgres: one `testcontainers.postgres.PostgresContainer("postgres:16-alpine",
  driver=None)` per session (`driver=None` makes `get_connection_url()` return a plain `postgresql://` URI psycopg
  accepts). Fresh database per test: on the container's admin URL run `CREATE DATABASE "t_<uuid hex>"` (autocommit)
  and point `DATABASE_URL` at it. Build the service with `monkeypatch.setenv("DATABASE_URL", url)` then
  `TestClient(create_app())`.
- "Restart" (AC-002.1, .2) is a second `create_app()` on the same `DATABASE_URL`; "two instances" (AC-002.3, .4) are
  two `create_app()` on the same URL. AC-002.4's simultaneous start: first requests of both instances from two
  threads at once.
- Database permanently down (AC-002.6 503 part, AC-002.8): `DATABASE_URL=postgresql://u:p@127.0.0.1:1/x` (refused
  at once). Down then back on the same URL (AC-002.6 "Lost task" check, AC-002.7, AC-002.9): pause the container
  (`container.get_wrapped_container().pause()`, later `.unpause()`); the host port mapping survives, connects then
  hit the 2 s connect timeout. Do not stop/start the container: its host port can change.
- AC-002.11: run the checks of AC-001.4, .5, .6, .8, .9, .11 with the Postgres-backed app on a fresh database.
- AC-002.10 (smoke): the existing `tests/test_smoke_tasks.py` runs unchanged against the public URL.
- Tests must depend on the `503` status, `Content-Type` and the exact body only, never on log output.

## Data

Table `tasks` exactly as in the spec's `### Storage` (`seq` identity for order, `id UUID PRIMARY KEY`, `title
VARCHAR(200) NOT NULL`, `due_date DATE NULL`), created by `PostgresTaskStore` on the first successful connection.
No migration tool; any later schema change gets its own idempotent step under the same lock (ADR-001). Nothing is
migrated from the in-memory store (AC-002.5).

## Risks

- A title containing U+0000 passes spec 001's validation but Postgres text cannot store it: that request answers
  `503` instead of `201`. Not covered by any criterion; changing validation would change spec 001's contract, so it
  is left as is and noted here.
- `DATABASE_URL` with a host name that resolves to several addresses multiplies the 2 s connect timeout per address;
  the platform's in-cluster Service name resolves to one ClusterIP, so the 5 s bound holds in deployed environments.
- A deployed instance without `DATABASE_URL` silently falls back to memory. `create_app()` logs the selected
  backend at info level (`event="task_store_selected"`, `backend="postgres"|"memory"`) so this is visible.
