# 002 — Persist tasks in Postgres behind the existing TaskStore, answering 503 when the database is down

## Problem

Spec 001 gave taskboard2 an API to create and list tasks, but the tasks live only in the API's memory: every restart or redeploy wipes them (AC-001.12), and the API cannot run more than one instance without each one holding its own list. The only way to use the system is to send HTTP requests by hand, because the taskboard2 web app still shows only its template page. Now that tasks are worth keeping, they should go into a database, and people should be able to see and add tasks in a browser.

## System context

Slice of the system plan `002-persist-tasks-in-postgres-and-manage` in `ika100-demo/taskboard2-gitops` for `taskboard2-api` (service-python). The system criteria and the contract below are binding: every criterion of this spec implements one of them and names it: `(system AC-<NNN>.<n>)`.

### System criteria

- **AC-002.1** Given tasks were created through `POST /tasks`, when the API restarts or is redeployed, then `GET /tasks` returns the same tasks with the same `id`, `title` and `due_date` as returned at creation, in the same order (oldest first). This replaces AC-001.12.
- **AC-002.2** Given tasks exist from before an API restart, when a new task is created after the restart, then its `id` differs from the `id` of every existing task.
- **AC-002.3** Given the API runs with 2 replicas (allowed in any environment; dev runs 1), when a task is created through one request, then every following `GET /tasks` contains that task, whichever replica answers.
- **AC-002.4** Given the persistent store of an environment has never held a task, when a caller sends `GET /tasks`, then the response is `200` with `[]`. Tasks that only existed in the memory of the previous API version are not carried over.
- **AC-002.5** Given the database is unreachable, when a caller sends `GET /tasks` or `POST /tasks` with a valid body, then the response is `503` with a JSON error body, and no task is created; when the database is reachable again, both requests succeed without restarting the API.
- **AC-002.6** Given the API is backed by the database, when the checks of AC-001.1 to AC-001.11 are run against it, then they all still pass (same status codes, fields, validation rules and error bodies).

### Contract

The API's HTTP contract is the one of spec 001 (system plan `docs/plan/001-create-and-list-tasks.md`, `## Contract`),
unchanged in fields, validation and `201`/`200`/`422` behaviour; this section restates what the web app needs and
adds the database-related parts.

### Base URL and configuration

- taskboard2-api: in-cluster `http://taskboard2-api` (Service port 80); dev public URL
  `http://taskboard2-api.taskboard2-dev.localhost:8088`. Reads `DATABASE_URL` (libpq URI, set by the platform from
  the `postgres` resource). Without `DATABASE_URL` it uses the in-memory store (tests and local runs only).
- taskboard2-web: reads `TASKBOARD2_API_URL` (no trailing slash; dev value `http://taskboard2-api`) on the server
  only. When it is unset, every API call counts as failed (AC-002.11 texts), and the app still starts and passes
  its probes.

### Task object

Exactly three fields: `id` (string, UUID4 canonical form, generated by the API, unique across restarts and
replicas), `title` (string, trimmed, 1 to 200 characters), `due_date` (`"YYYY-MM-DD"` or `null`, always present).

### `GET /tasks`

- `200` with a JSON array of task objects, oldest first (creation order), every task in the database; `[]` when
  empty.
- `503` when the database is unreachable or fails (body under Errors).

### `POST /tasks`

Request: JSON object, `Content-Type: application/json`, `title` (required string) and `due_date` (optional,
`"YYYY-MM-DD"` or `null`); the web app sends `due_date` as `null` when the date field is empty, and `title` exactly
as typed.

- `201` with the created task object.
- `422` on invalid input, validated before the database is touched (so an invalid body gives `422` even when the
  database is down).
- `503` when the database is unreachable or fails; no task is stored.

### Storage (taskboard2-api only)

```sql
CREATE TABLE IF NOT EXISTS tasks (
  seq      BIGINT GENERATED ALWAYS AS IDENTITY UNIQUE,  -- creation order
  id       UUID PRIMARY KEY,
  title    VARCHAR(200) NOT NULL,
  due_date DATE NULL
);
```

- `GET /tasks` is `SELECT id, title, due_date FROM tasks ORDER BY seq`.
- The schema is created by the API itself, idempotently, under `pg_advisory_lock` so two replicas starting at once
  do not race; it runs on the first successful database connection, not as a hard startup requirement.

### Web page (taskboard2-web)

- `GET /` renders: a list (`<ul>`/`<li>`, one item per task, title then due date) or "No tasks yet." or "Tasks could
  not be loaded. Please try again later."; and the create form (title field labelled "Title", date field labelled
  "Due date", submit button "Add task").
- Field errors from a `422` are shown next to their field; the generic save error of AC-002.11 is shown above the
  submit button.

### Errors

- `422` (API): the spec 001 format `{"detail": [{"loc": [...], "msg": str, "type": str}]}`; callers depend only on the
  status and the last element of each `loc` (`"title"` or `"due_date"`; `["body"]` or `["body", <pos>]` for a body
  that is not a JSON object).
- `503` (API, new): `Content-Type: application/json`, body `{"detail": "Task store unavailable"}`. Callers depend on
  the status only, not the text. Raised for any connection, pool-timeout or query error of the database.
- Any other status, a non-JSON body, a body that does not match the shapes above, a timeout or a connection error is
  a failed call. The web app treats a failed `GET /tasks` like `503` (load error text) and a failed `POST /tasks`
  like `503` (save error text, inputs kept); on a `422` whose `loc` names no known field, it shows the save error
  text. It never assumes a failed `POST` did not create the task; the next page load shows the truth.
- The web app logs failed API calls server-side (status, duration) and never forwards API bodies to the browser.

### Timeouts

- Web to API: 5 s per request (`AbortSignal.timeout(5000)`), for both `GET /tasks` and `POST /tasks`; no retry. A
  timed-out or refused call is a failed call (Errors). A retry by the user after a timed-out `POST` may create a
  duplicate, which AC-001.6 allows.
- API to database: connect timeout 2 s, pool checkout timeout 2 s, `statement_timeout` 3 s, so the API answers
  `503` well inside the web app's 5 s. The pool drops broken connections and reconnects on the next request
  (AC-002.5), with no restart and no background retry loop.
- When the API is down or restarting, the Gateway or the in-cluster Service refuses the connection or answers
  `502`/`503`: the web app shows its error texts and keeps serving its page and probes. When the database is down,
  the API stays ready and answers `503` with the JSON body.
- Smoke tests: 10 s per request (API, as in spec 001); Playwright's default timeouts (web).

### Provided by the system

The gitops part of this plan wires these for this repo; rely on them, do not ask for them again:

- resource `postgres`: env `DATABASE_URL`, `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`
- exposed through the Gateway at host `taskboard2-api`

## Stories

As a caller of the taskboard2 API (including the taskboard2 web app), I want the tasks I created to still be there after the API restarts or is redeployed, so that recorded work is never lost by a deploy.

As an operator of taskboard2, I want any number of API replicas (up to 2 today) to show the same list of tasks, so that the API can be scaled without callers seeing different lists.

As a caller of the taskboard2 API, I want a clear `503` with a JSON body when the database is unavailable, and normal answers again as soon as it is back, so that I can show an error and retry instead of getting a hang, a half-created task or an API that needs a restart.

As a caller of the taskboard2 API, I want every request and response of spec 001 to behave exactly as before, so that nothing I built against it breaks.

## Acceptance criteria

- **AC-002.1** Given a service backed by a database in which tasks A, B and C were created through `POST /tasks` in that order, when the service is restarted (a new service instance is started on the same database) and a caller sends `GET /tasks`, then the response is `200` with an array whose elements are equal to the objects returned at creation of A, B and C (same `id`, `title` and `due_date`), in the order A, B, C. (system AC-002.1)
- **AC-002.2** Given a service backed by a database in which tasks were created and the service was then restarted on the same database, when a caller creates a new task with `POST /tasks`, then the response is `201` and the new task's `id` differs from the `id` of every task created before the restart, and `GET /tasks` lists the new task after all of them. (system AC-002.2)
- **AC-002.3** Given two service instances backed by the same database, when a task is created with `POST /tasks` on the first instance, then `GET /tasks` on the second instance returns an array with exactly one element with that `id`, equal to the object returned at creation; and the same holds the other way round (created on the second, listed on the first), with both instances returning the same tasks in the same order. (system AC-002.3)
- **AC-002.4** Given a database that has never held the task data and two service instances started on it at the same time, when a caller then sends `GET /tasks` and `POST /tasks` with `{"title": "Buy milk"}` to each instance, then neither instance fails to start, every `GET /tasks` answers `200` and every `POST /tasks` answers `201`, and afterwards both instances list both created tasks. (system AC-002.3)
- **AC-002.5** Given a service backed by a database that has never held a task, when a caller sends `GET /tasks`, then the response is `200` with the body `[]` (tasks held only in the memory of a previous service version are not carried over). (system AC-002.4)
- **AC-002.6** Given a running service whose database is unreachable, when a caller sends `GET /tasks`, or `POST /tasks` with the valid body `{"title": "Lost task"}`, then each response arrives within 5 seconds and is `503` with `Content-Type: application/json` and the body `{"detail": "Task store unavailable"}`; and once the database is reachable again, `GET /tasks` contains no task with title `"Lost task"`. (system AC-002.5)
- **AC-002.7** Given a running service that answered `503` because its database was unreachable, when the database is reachable again and a caller sends `POST /tasks` with `{"title": "Back again"}` and then `GET /tasks` to the same service instance, without restarting it, then the responses are `201` and `200`, and the list contains the new task. (system AC-002.5)
- **AC-002.8** Given a running service whose database is unreachable, when a caller sends `POST /tasks` with an invalid body (for example `{"title": ""}` or `{"title": "Buy milk", "due_date": "tomorrow"}`), then the response is `422` with a `detail` entry whose `loc` ends with the offending field (`"title"` or `"due_date"`), not `503`. (system AC-002.5)
- **AC-002.9** Given the database is unreachable when the service starts, when a caller sends `GET /health` and `GET /ready`, then the service is running and both answer `200`, and `GET /tasks` answers `503` as in AC-002.6; when the database then becomes reachable, `GET /tasks` answers `200` and `POST /tasks` with a valid body answers `201` on the same instance, without a restart. (system AC-002.5)
- **AC-002.10** Given the service is deployed backed by the database and reached through its public URL, when the checks of AC-001.1, AC-001.2, AC-001.3, AC-001.7 and AC-001.10 are run against it (finding their own task by `id` and never assuming an empty list), then they all pass with the same status codes, fields and error bodies as in spec 001. (system AC-002.6) (smoke)
- **AC-002.11** Given a service backed by a fresh, empty database, when the checks of AC-001.4, AC-001.5, AC-001.6, AC-001.8, AC-001.9 and AC-001.11 are run against it, then they all pass with the same status codes, fields, validation rules and error bodies as in spec 001 (spec 001's `GET /tasks` on a freshly started service corresponds to a fresh database here). (system AC-002.6)

## Non-goals

- Migrating tasks held in memory by the previous API version (system AC-002.4).
- AC-001.12 (empty list after a restart) no longer holds when the service is backed by a database; AC-002.1 replaces it.
- Running without a database configured in a deployed environment: without database configuration the service keeps the in-memory store of spec 001, for in-process tests and local runs only.
- Reporting database health through `/ready`: the readiness check stays independent of the database, so callers get the JSON `503` of AC-002.6 rather than a Gateway error.
- Retrying database calls inside a request or in the background; a request during an outage answers `503` and the next request tries again.
- Changes to the HTTP contract of spec 001 other than the new `503`: no new fields, filters, pagination, updates, deletes, authentication or idempotency keys.
- Scaling dev beyond 1 replica (a gitops decision; 2 replicas are supported, AC-002.3).
